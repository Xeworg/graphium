# F0 — Informe del spike técnico

Informe del spike F0 del PRD v1.7 (§12). F0 no construye producto: **cierra
decisiones** con un camino end-to-end real y midiendo lo que hay que medir.

- Especificación: `docs/PRD.md`
- Documento de feature: `odd/tasks/f0-spike-tecnico.md` (tareas y specs `S#`)
- Rama: `feature/f0-spike-tecnico`

## 1. Qué se probó

El camino completo, sin atajos:

```
JSON del agente → schema (schemars) → validate() → IR → medida de texto
→ layout (dagre) → SVG propio → plano con grilla en la ventana
```

La puerta única es `gx_core::engine::render_json` (§9.1, RNF6): `gx-mcp` y los
tests usan exactamente esa función, así que ningún test del motor necesita
Tauri, webkit ni un webview.

### Las piezas

| Crate | Qué aporta | Specs |
|---|---|---|
| `gx-core` | IR, errores con codes estables, trait `DiagramKind`, registro, `fmt_num`, tokens congelados, puerta única | S3-S7 |
| `gx-kinds` | El kind `graph`: schema, reglas cruzadas y traducción a la IR | S13 |
| `gx-render-svg` | Métricas con `rustybuzz` + Inter 400/600 y el SVG determinista | S7-S9, S11, S12 |
| `gx-layout` | `DagreEngine` detrás del trait `LayoutEngine` + matriz de capacidades | S10, S11, S20 |
| `gx-mcp` | Servidor MCP por stdio con `render_diagram` + `mcp-config` | S14, S15, S21 |
| `gx-app` | La ventana-plano: grilla, cámara, round-trip, socket single-instance | S1, S16-S19, S22, S23 |

## 2. Decisiones que se cerraron

| Decisión | Cómo quedó | Dónde |
|---|---|---|
| ¿Layout trivial o `dagre` real? | **`dagre` real** (0.1.2 pineado): con posiciones fijas la matriz de capacidades no probaría nada | S10, L4 |
| ¿Dónde viven los traits del motor? | En `gx-core`, no en `gx-layout` ni en `gx-render-svg`: `gx-core` no puede depender de nadie y a la vez la puerta única vive ahí | L6 |
| ¿Cómo llegan los motores a la puerta? | **Inyección global** (`engine::install`): `gx-core` no puede conocer `dagre` ni `rustybuzz` | L7 |
| ¿Cómo resuelve el registro un kind por nombre? | Con un `KindHandler` **object-safe** (`KindAdapter<K>`): el trait del PRD tiene `fn schema()` estático y no es object-safe | L9 |
| ¿Qué escribe el SVG? | Nuestro: sin `<rect>` de fondo, sin declaración XML, `viewBox` en unidades de plano, `fmt_num` en todo número, ids derivados de la IR | S7 |
| ¿Cómo se dibuja la grilla? | **CSS gradient** (dos `repeating-linear-gradient`), capa fija, `--grid-step = 31.26 px × zoom`, grosor 1 px de pantalla | S23, L11, L16 |
| ¿Qué mide "separación 59 px"? | La **diagonal mayor** del rombo → paso perpendicular `59 · sin(32°) ≈ 31.26 px` | S23 |
| ¿Dónde vive la cámara? | En el frontend. Rust guarda una copia (`CameraSnapshot`) que el frontend empuja con `camera-changed` | S19 |
| ¿Cómo se serializa el IR? | `kind_data` con `BTreeMap<String, IrValue>` (no `&'static str`) para que `--dump-last` pueda serializarla | L10 |
| ¿Versión de `schemars`? | 1.2.3: el schema se llama `Schema`, no `RootSchema` | L8 |
| ¿Qué permisos tiene el frontend? | Tauri 2 exige una **capability**: `core:event:allow-emit` + `core:event:allow-listen` en `crates/gx-app/capabilities/default.json`. Sin eso el webview no puede emitir eventos y `rendered` queda siempre en `false` | L18 |
| ¿El CSP rompe el IPC? | **No**: con `default-src 'self'` el script de IPC de Tauri se inyecta igual (Tauri modifica el CSP del protocolo de assets). El SVG se inserta con `innerHTML` sin scripts inline | L18 |

## 3. La matriz de capacidades de `dagre`

Cada capacidad con su test, como pide §8.4. Los tests viven en
`crates/gx-layout/tests/capabilities.rs` y `crates/gx-layout/tests/rnf1_bis.rs`.

| Capacidad | Soportada | Cómo se prueba |
|---|---|---|
| Direcciones TB / BT / LR / RL | Sí | TB y LR tienen forma propia (TB alto, LR ancho); BT y RL producen layout no vacío |
| Clusters (grupos) | Sí | el cluster aparece en `layout.groups` y su bbox contiene a sus miembros |
| Labels en edges | Sí | la arista con label recibe `label_at`; sin label, no |
| Self-loops | Sí | la arista `a → a` produce una ruta de 3 o más puntos |
| Nodos desconectados | Sí | el nodo aislado queda colocado dentro del bbox del dibujo |
| Determinismo | Sí | dos layouts del mismo grafo son idénticos (nodos, aristas y bbox) |

**Limitación conocida:** dos aristas con el mismo origen y destino comparten
el id de SVG `m-<from>-<to>` (el renderer no desambigua edges paralelos). No
afecta al layout: `dagre` las routea por separado porque el grafo es
multigraph.

## 4. La medición RNF1-bis

Los cuatro casos fijos de §7.3, con `DagreEngine` en frío (sin caché de
layout, por diseño determinista). Medición en release en la máquina de
desarrollo (Fedora 44, x86_64), no en la máquina de referencia del CI: los
números son una señal de orden de magnitud, no el valor que gatea el CI.

| Caso | Objetivo p95 | Medido | Margen |
|---|---|---|---|
| `100n/150e` sin grupos | < 500 ms | **53.7 ms** | 9,3× |
| `100n/400e` sin grupos | < 500 ms | **133.4 ms** | 3,7× |
| `100n/150e` + 8 clusters | < 500 ms | **206.6 ms** | 2,4× |
| `300n/600e` sin grupos | < 1.5 s | **260.0 ms** | 5,8× |

Reproducir: `cargo test --release -p gx-layout -- --ignored --nocapture`.

## 5. Go / no-go de `dagre`

**GO para F1.** `dagre` 0.1.2 cumple la matriz de capacidades completa
(clusters, las cuatro direcciones, labels en edges, self-loops y nodos
desconectados) y está dos a nueve veces por debajo de los presupuestos de
RNF1-bis, incluso con clusters, que es el caso más caro.

Plan operativo (§8.4), que se mantiene:

- **Pin exacto** de versión: `dagre = "=0.1.2"` en el workspace.
- **Trigger de vendoring**: si F1 queda bloqueada por un defecto de upstream
  y no hay fix en dos semanas, vendorizar el crate al workspace con su
  atribución NOTICE.
- **Riesgo residual**: el crate es un port reciente (sigue a dagre.js
  3.0.1-pre) y su API puede cambiar; el aislamiento detrás de `LayoutEngine`
  limita el daño a `gx-layout`.
- **El no-go no aplica**: no hay ninguna capacidad del §8.4 que falte.

## 6. El presupuesto de binario (RNF1-quater)

Medición con `cargo build --release` + `strip` (el perfil de release ya
trae `strip = true`, `lto = true` y `opt-level = "z"`):

| Componente | Presupuesto | Medido |
|---|---|---|
| Binario completo | 15.700.000 bytes | **5.318.976 bytes (5,32 MB)** |

Margen: **10,4 MB**. La app con Tauri, el motor de layout, el renderer SVG,
las fuentes embebidas (116 KB en total) y el runtime de MCP entran en un
tercio del presupuesto, así que F1 tiene espacio para `resvg` (PNG) y para
los kinds que falten sin tocar RNF1-quater.

Pendiente para F1: la medición tiene que correr en la imagen de CI del
workflow (`.github/workflows/ci.yml`, job `test`, paso «Binary budget»), que
ya falla el build por encima de 15.700.000 bytes.

## 7. Lo que F0 no resolvió (queda para F1)

- Los kinds `graph` + `er` completos, `validate_diagram`, `update_diagram`,
  `list_diagrams`, `get_diagram`, `export_diagram` y `get_diagram_schema`
  (PRD §12, F1).
- La escalera de degradación y `opts.extract` (RF20-bis, F1).
- Varios diagramas en el plano, panel lateral y cierre por ítem (RF26-RF28,
  F2).
- Los golden-SVG con hash en CI (F1) y el presupuesto de bytes del SVG
  (RNF1-ter).

## 8. Cómo reproducir

```bash
cargo test --workspace                  # suite completa
cargo test -p gx-layout -- --nocapture   # matriz de capacidades
cargo test --release -p gx-layout -- --ignored --nocapture   # medición RNF1-bis
cargo build --release --bin graphium && ./target/release/graphium mcp-config
```
