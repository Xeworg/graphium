# F0 — Informe del spike técnico

Informe del spike F0 del PRD v1.7 (§12). F0 no construye producto: **cierra
decisiones** con un camino end-to-end real y midiendo lo que hay que medir.

- Especificación: `docs/PRD.md`
- Documento de feature: `odd/tasks/f0-spike-tecnico.md` (tareas y specs `S#`)
- Rama: `feature/f0-spike-tecnico`

## 1. Qué se probó

El camino completo, sin atajos:

```
JSON del agente → schema (schemars) → validate() → IR → medida de texto
→ layout (dagre) → SVG propio → plano con grilla en la ventana
```

La puerta única es `gx_core::engine::render_json` (§9.1, RNF6): `gx-mcp` y los
tests usan exactamente esa función, así que ningún test del motor necesita
Tauri, webkit ni un webview.

### Las piezas

| Crate | Qué aporta | Specs |
|---|---|---|
| `gx-core` | IR, errores con codes estables, trait `DiagramKind`, registro, `fmt_num`, tokens congelados, puerta única | S3-S7 |
| `gx-kinds` | El kind `graph`: schema, reglas cruzadas y traducción a la IR | S13 |
| `gx-render-svg` | Métricas con `rustybuzz` + Inter 400/600 y el SVG determinista | S7-S9, S11, S12 |
| `gx-layout` | `DagreEngine` detrás del trait `LayoutEngine` + matriz de capacidades | S10, S11, S20 |
| `gx-mcp` | Servidor MCP por stdio con `render_diagram` + `mcp-config` | S14, S15, S21 |
| `gx-app` | La ventana-plano: grilla, cámara, round-trip, socket single-instance | S1, S16-S19, S22, S23 |

## 2. Decisiones que se cerraron

| Decisión | Cómo quedó | Dónde |
|---|---|---|
| ¿Layout trivial o `dagre` real? | **`dagre` real** (0.1.2 pineado): con posiciones fijas la matriz de capacidades no probaría nada | S10, L4 |
| ¿Dónde viven los traits del motor? | En `gx-core`, no en `gx-layout` ni en `gx-render-svg`: `gx-core` no puede depender de nadie y a la vez la puerta única vive ahí | L6 |
| ¿Cómo llegan los motores a la puerta? | **Inyección global** (`engine::install`): `gx-core` no puede conocer `dagre` ni `rustybuzz` | L7 |
| ¿Cómo resuelve el registro un kind por nombre? | Con un `KindHandler` **object-safe** (`KindAdapter<K>`): el trait del PRD tiene `fn schema()` estático y no es object-safe | L9 |
| ¿Qué escribe el SVG? | Nuestro: sin `<rect>` de fondo, sin declaración XML, `viewBox` en unidades de plano, `fmt_num` en todo número, ids derivados de la IR | S7 |
| ¿Cómo se dibuja la grilla? | **CSS gradient** (dos `repeating-linear-gradient` a ±32°), capa fija, `--grid-step = 31.26 px × zoom`, grosor 1 px de pantalla | S23, L11 |
| ¿Qué mide "separación 59 px"? | La **diagonal mayor** del rombo → paso perpendicular `59 · sin(32°) ≈ 31.26 px` | S23 |
| ¿Dónde vive la cámara? | En el frontend. Rust guarda una copia (`CameraSnapshot`) que el frontend empuja con `camera-changed` | S19 |
| ¿Cómo se serializa el IR? | `kind_data` con `BTreeMap<String, IrValue>` (no `&'static str`) para que `--dump-last` pueda serializarla | L10 |
| ¿Versión de `schemars`? | 1.2.3: el schema se llama `Schema`, no `RootSchema` | L8 |

## 6. Lo que F0 no resolvió (queda para F1)

- Los kinds `graph` + `er` completos, `validate_diagram`, `update_diagram`,
  `list_diagrams`, `get_diagram`, `export_diagram` y `get_diagram_schema`
  (PRD §12, F1).

  F2).

  (RNF1-ter).

## 7. Cómo reproducir

```bash
cargo test --workspace                  # suite completa
cargo test -p gx-layout -- --nocapture   # matriz de capacidades
cargo test --release -p gx-layout -- --ignored --nocapture   # medición RNF1-bis
cargo build --release --bin graphium && ./target/release/graphium mcp-config
```
